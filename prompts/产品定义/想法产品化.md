# 想法产品化

## 用途

把一个模糊想法一次性整理成可讨论、可评审、可进入 MVP 设计的产品方案。适用于软件产品、内部系统、AI 工具和行业应用。

## 输入变量

- `IDEA`：原始想法或问题描述，必填
- `TARGET_USERS`：已知目标用户，可空
- `BUSINESS_CONTEXT`：业务背景、现有流程或替代方案，可空
- `CONSTRAINTS`：时间、预算、技术、合规、部署环境等限制，可空
- `PRODUCT_STAGE`：概念验证 / MVP / 已有产品改造，默认 MVP

## 可复制 Prompt

```text
你是一名务实的产品负责人。请把下面的模糊想法整理成一份可评审的产品化方案。

输入：
<IDEA>
{{IDEA}}
</IDEA>

<TARGET_USERS>
{{TARGET_USERS}}
</TARGET_USERS>

<BUSINESS_CONTEXT>
{{BUSINESS_CONTEXT}}
</BUSINESS_CONTEXT>

<CONSTRAINTS>
{{CONSTRAINTS}}
</CONSTRAINTS>

<PRODUCT_STAGE>
{{PRODUCT_STAGE}}
</PRODUCT_STAGE>

执行要求：
1. 先复述你对想法的理解，并区分“用户已明确的信息”“合理假设”“仍待确认的信息”。
2. 不编造市场规模、竞品数据、用户数量或商业结果。没有外部检索依据时，只能描述竞品类型和替代方式。
3. 重点寻找最小可验证闭环，不要把所有可能功能都塞进 MVP。
4. 每项功能必须能对应到具体用户、场景、问题和验收结果。
5. 涉及状态流转、权限、数据对象、异步任务或外部系统时，必须明确边界和异常情况。
6. 不要停在提问阶段。信息不足时使用明确标注的假设完成草案，并把真正会改变方案的问题放到最后。

请按以下结构输出：

# 1. 决策摘要
- 一句话定位
- 目标用户
- 核心问题
- 产品提供的关键价值
- 建议是否进入 MVP：是 / 否 / 需先验证
- 主要判断依据

# 2. 用户与场景
用表格列出：用户角色、触发场景、当前做法、主要痛点、期望结果、使用频率。
补充 3–5 条 JTBD，格式为“当……时，我想……，以便……”。

# 3. 问题与价值假设
列出：
- 已验证事实
- 尚未验证的关键假设
- 最危险假设
- 推荐的低成本验证方式

# 4. 产品边界
分别列出：
- MVP 必须做
- MVP 明确不做
- 后续可能扩展
- 容易发生范围蔓延的红线

# 5. 核心业务闭环
用 5–8 步描述从触发到结果的主流程。
存在明显状态变化时，给出 Mermaid 状态图；否则给出 Mermaid 流程图。图中节点不超过 15 个。

# 6. 核心对象与规则
用表格列出：对象、用途、关键字段、状态、归属方、生命周期。
补充关键业务规则、权限规则、幂等要求、失败重试和数据保留要求。

# 7. 页面或交互入口
列出不超过 8 个页面或入口。每项包含：目标用户、页面目的、核心信息、关键操作、异常状态。
非软件产品可改为服务触点或交付物。

# 8. MVP 功能与验收
用表格列出：功能、用户价值、优先级、前置条件、验收标准。
至少给出 6 条 Given-When-Then 验收标准，覆盖正常流程、权限不足、重复提交、外部依赖失败和空数据。

# 9. 指标设计
给出：
- 1 个北极星指标
- 3–5 个过程指标
- 2–4 个质量或安全护栏指标
说明每个指标如何采集，避免只写无法测量的口号。

# 10. 技术与交付可行性
说明建议的系统边界、主要模块、数据存储、外部依赖、部署形态和安全边界。
只做产品级技术草图，不虚构具体接口或数据库结构。

# 11. 风险与验证计划
按“风险、影响、发生条件、验证方式、缓解措施、负责人建议”输出表格，并标记 P0–P3。

# 12. 路线图
给出：
- 1–2 周验证阶段
- MVP 阶段
- 上线后迭代阶段
每阶段写明目标、交付物和退出条件，不给没有依据的具体日期。

# 13. 待确认问题
最多提出 7 个真正会改变产品方向、范围或成本的问题，并说明每个问题会影响什么决策。
```

## 使用说明

- 这是一份单次生成 Prompt，不负责多轮项目管理。
- 需要继续细化需求、状态机和页面规格时，应转入软件设计类 Skill。
- 竞品、市场和定价结论需要单独检索与事实核验。
