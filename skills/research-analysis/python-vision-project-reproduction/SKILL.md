# Python 视觉算法项目复现

## description

将一个公开的 Python 计算机视觉项目，从“看起来能运行”推进到“在指定本地环境中可重复运行、结果可核验、资源消耗可接受”。适用于目标检测、图像分类、分割、姿态估计、跟踪、OCR、人脸、视频理解、三维重建和多模态视觉项目。

该 Skill 强调区分四件事：官方 Demo 能否运行、官方权重能否推理、本地数据能否适配、训练结果能否复现。不能把成功显示一张示例图等同于项目已经复现。

## input

- 项目仓库、论文、项目页或模型页面
- 复现目标：Demo、推理、评测、微调、完整训练或业务改造
- 本地系统：Windows、WSL、Linux 或 Docker
- Python、CUDA、驱动、PyTorch/TensorFlow 版本
- GPU 型号、显存、内存、磁盘和网络条件
- 输入数据类型：图片、视频、摄像头、数据集或业务样本
- 期望输出和评价指标
- 是否允许下载权重、数据集和编译扩展
- 时间、存储和计算预算

## workflow

### 01 定义复现级别

先选择本次真正要完成的级别：

- L0：理解项目用途和输入输出
- L1：安装环境并通过导入检查
- L2：使用官方权重跑通官方 Demo
- L3：在用户自己的图片或视频上推理
- L4：在标准数据集上执行官方评测
- L5：使用小数据集完成微调
- L6：复现论文或项目公布的主要训练结果
- L7：改造成稳定可部署的业务服务

默认优先完成 L2 和 L3，再决定是否继续训练。

### 02 核对项目真实性与维护状态

检查：

- 仓库是否为官方实现
- README、论文和权重是否对应
- 最近提交、Release 和 Issue 状态
- 是否只有演示代码，没有训练或评测代码
- 权重、数据集和配置是否仍可下载
- 许可证是否允许当前用途
- 是否依赖私有数据、API 或未发布模块

把结论标记为：

- 官方明确提供
- 社区补充
- 根据代码推断
- 尚未确认

### 03 建立项目结构图

定位：

- 推理入口
- 训练入口
- 评测入口
- 配置文件
- 模型定义
- 数据加载和增强
- 损失函数
- 后处理
- 权重加载
- 可视化与结果保存
- 自定义 CUDA/C++ 算子
- 示例资源和测试

输出从命令入口到最终结果的真实调用链，不只列目录。

### 04 建立兼容矩阵

记录并核对：

| 层级 | 项目要求 | 本地实际 | 处理方式 |
| --- | --- | --- | --- |
| 操作系统 | Linux/Windows | 实际系统 | 原生、WSL 或 Docker |
| Python | 项目要求版本 | 当前版本 | 新建隔离环境 |
| GPU 驱动 | 最低要求 | 当前驱动 | 保持或升级 |
| CUDA | 编译/运行版本 | 当前版本 | 使用框架自带运行时或本地编译 |
| 深度学习框架 | PyTorch/TensorFlow | 当前版本 | 锁定匹配版本 |
| 编译器 | GCC/MSVC | 当前版本 | 按扩展要求调整 |
| 关键库 | OpenCV、MMCV 等 | 当前版本 | 锁版本并验证 |

必须区分：

- NVIDIA 驱动版本
- 系统 CUDA Toolkit
- PyTorch 自带 CUDA Runtime
- 项目扩展编译所用 CUDA

### 05 设计隔离环境

优先选择：

1. `venv` 或 Conda 独立环境
2. 锁定 Python 和主要框架版本
3. 保存完整安装命令
4. 对自定义算子记录编译参数
5. 保留 `requirements-lock.txt`、`environment.yml` 或等价依赖快照

不能直接污染现有开发环境，也不能先无差别升级全部依赖。

### 06 最小安装验证

安装后依次验证：

- Python 可执行文件和环境路径正确
- 深度学习框架可导入
- CUDA 是否可用
- GPU 名称和显存可见
- OpenCV、NumPy 和项目核心包可导入
- 自定义算子是否成功加载
- 项目 CLI 或模块入口能显示帮助

发生错误时记录：

- 完整命令
- 关键报错
- 根因判断
- 修改内容
- 修改后的验证结果

### Gate ① 环境可重复

进入推理前必须确认：

- 使用的是明确的隔离环境
- Python 和框架版本已记录
- GPU/CUDA 检查通过，或明确选择 CPU
- 安装过程不存在未记录的手工修改

### 07 获取并校验模型资源

对于权重、配置和数据：

- 优先使用官方链接
- 记录文件名、版本和来源
- 校验文件大小，条件允许时记录哈希
- 确认权重对应的模型配置、类别数和输入方式
- 不把不同版本权重和配置混用
- 对需要登录、授权或许可证的数据集明确说明

### 08 跑通官方最小 Demo

使用一个官方样例完成：

```text
输入读取
→ 预处理
→ 模型加载
→ 推理
→ 后处理
→ 可视化或结构化结果
→ 文件保存
```

记录：

- 完整命令
- 输入文件
- 输出路径
- 推理设备
- 首次加载时间
- 单次或平均耗时
- 峰值显存
- 结果是否符合官方示例的方向

### Gate ② 官方链路跑通

只有同时满足以下条件才算官方 Demo 成功：

- 命令正常退出
- 输出文件实际存在
- 输出不是空结果或错误占位
- 使用了预期权重和配置
- 关键日志无隐藏失败

### 09 适配用户数据

使用用户自己的图片或视频测试：

- 文件格式和编码
- 分辨率和长宽比
- 色彩空间
- 类别映射
- 置信度阈值
- NMS 或其他后处理参数
- 视频帧率和抽帧策略
- 批处理方式
- 输入输出路径的中文、空格和跨平台兼容性

输出至少一组成功样本和一组失败或边界样本。

### 10 测量资源和性能

至少记录：

- 模型参数量或权重大小
- 输入尺寸
- 精度模式：FP32、FP16、BF16、INT8
- Batch Size
- 峰值显存
- 单图耗时或视频 FPS
- CPU、内存和磁盘占用
- 首次加载与稳定运行差异

显存不足时按顺序尝试：

1. 关闭训练，仅推理
2. 使用 `eval` 和无梯度模式
3. 降低 Batch Size
4. 降低输入分辨率
5. 使用半精度
6. 使用更小模型
7. 启用梯度累积或检查点
8. 最后再考虑 CPU 或切分处理

### 11 执行官方评测

当目标包含精度验证时：

- 使用官方数据划分
- 使用正确类别映射
- 核对输入尺寸和预处理
- 核对评价脚本版本
- 区分单尺度、多尺度和测试时增强
- 保存原始指标和日志

不能使用少量肉眼样本代替正式评测。

### 12 制定训练或微调方案

训练前核对：

- 数据目录和标注格式
- 类别数和标签定义
- 数据增强
- 预训练权重
- 学习率、Batch Size 和训练轮数
- 冻结策略
- 优化器和调度器
- 混合精度
- 保存、恢复和最佳模型规则
- 验证集和评价指标

优先先做小样本过拟合测试：确认模型能够在极小数据集上降低损失并得到合理结果，再启动长时间训练。

### Gate ③ 训练链路可信

启动正式训练前必须通过：

- 数据加载可视化正确
- 标签与类别映射正确
- 一个前向和反向步骤成功
- 小样本过拟合趋势正常
- Checkpoint 可以保存和恢复
- 显存与预计训练时间可接受

### 13 分析结果差异

将结果分类：

- 完全复现
- 工程链路跑通，但未达到官方指标
- 指标趋势一致，数值存在差异
- 仅完成官方权重推理
- 因资源限制采用降配方案
- 因权重、数据或代码缺失无法复现

差异分析应覆盖：

- 代码和配置版本
- 数据划分
- 随机种子
- 硬件和精度模式
- 依赖版本
- 未公开训练技巧
- 官方指标是否使用额外数据或增强

### 14 业务化改造评估

当目标是部署而非论文复现时，继续分析：

- 模型初始化与复用
- 图片、视频流和摄像头输入
- 并发和队列
- 批处理
- 服务接口
- 超时和错误码
- 资源隔离
- 模型热更新
- 日志和指标
- ONNX、TensorRT、OpenVINO 等导出路径
- 许可证和商用限制

## rules

1. 不把 README 中的命令未经验证直接认定为可运行。
2. 不把官方权重推理成功等同于训练结果可复现。
3. 不盲目安装最新版依赖；优先建立版本兼容矩阵。
4. 不混淆驱动、CUDA Toolkit 和框架自带 CUDA Runtime。
5. 不通过删除版本限制、吞异常或关闭核心算子来伪造成功。
6. 不在未验证标签和数据加载前启动长时间训练。
7. 不只报告“运行成功”，必须保存命令、环境、输出和性能证据。
8. 不根据 GPU 型号直接判断能否运行；结合模型、分辨率、Batch Size 和精度模式分析。
9. 不擅自下载来源不明的可执行文件、权重和数据。
10. 修改上游代码时必须记录补丁，不直接覆盖而不留痕。
11. 涉及人脸、人员行为和敏感场景数据时，必须说明隐私、授权和误判风险。
12. 无法确认的信息明确标为待验证，不编造参数和指标。

## output

最终输出至少包含：

- 项目用途和适用场景
- 官方程度与维护状态
- 项目结构和关键调用链
- 本地兼容矩阵
- 可重复环境安装步骤
- 官方 Demo 命令及验证结果
- 用户数据推理结果
- 性能和显存记录
- 评测或训练结果
- 与官方结果的差异
- 修改过的文件和补丁说明
- 已知问题与未确认信息
- 下一阶段建议

推荐保存以下文件：

```text
reproduction/
├── README.md                 # 复现结论与完整命令
├── environment.yml           # Conda 环境，按实际情况选择
├── requirements-lock.txt     # 锁定依赖，按实际情况选择
├── commands.md               # 安装、推理、评测、训练命令
├── patches/                  # 对上游代码的修改
├── samples/input/            # 测试输入
├── samples/output/           # 测试输出
├── logs/                     # 运行日志
└── results/metrics.json      # 指标和性能结果
```

## examples

### 在 RTX 3060 12GB 上复现目标检测项目

```text
复现该 Python 视觉算法仓库，环境为 Windows 11 + WSL2 Ubuntu，GPU 为 RTX 3060 12GB。

目标：
1. 使用官方权重跑通图片和 MP4 视频推理；
2. 在我的业务图片上验证检测效果；
3. 测量 1080P 输入下的显存和速度；
4. 判断能否使用小数据集进行微调；
5. 输出可直接交给 Codex 执行的完整步骤。

执行要求：
- 先核对仓库、论文、权重和许可证是否对应；
- 建立 Python、PyTorch、CUDA 和自定义算子的兼容矩阵；
- 使用独立环境，不修改系统 Python；
- 先跑官方最小 Demo，再测试自有数据；
- 保存完整安装和运行命令；
- 记录峰值显存、单图耗时和视频 FPS；
- 如需改代码，把修改保存为补丁并解释原因；
- 正式训练前必须完成数据可视化、小样本过拟合和 Checkpoint 恢复测试；
- 最终明确区分：已验证、推断、未验证和受硬件限制的内容。
```

### 视觉项目失败排查

```text
该项目安装后出现自定义 CUDA 算子加载失败。不要直接降级或升级全部依赖。

请按以下顺序处理：
1. 输出当前驱动、Python、PyTorch、PyTorch CUDA Runtime、系统 CUDA Toolkit 和编译器版本；
2. 对照项目要求建立兼容矩阵；
3. 定位扩展的构建脚本和编译日志；
4. 判断是 ABI、CUDA 版本、编译器、架构列表还是缓存问题；
5. 采用最小修改修复并重新编译；
6. 执行算子导入、最小推理和官方 Demo 三层验证；
7. 记录完整命令、修改文件和剩余风险。
```
