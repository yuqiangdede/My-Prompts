# 深度调研与事实核验

## description

围绕技术、产品、政策、市场或项目主题开展可追溯的网络调研。通过问题拆解、来源分级、交叉验证和结论置信度控制，避免把搜索摘要拼接成报告。

## input

- 调研问题
- 时间范围与地区范围
- 目标读者
- 需要回答的决策
- 必须覆盖或排除的来源
- 输出深度、格式和截止日期

## workflow

### 01 定义研究问题

把宽泛主题改写为：

- 核心问题
- 子问题
- 判断标准
- 需要核实的关键事实
- 最终要支持的决策

### 02 制定检索矩阵

至少覆盖：

- 官方文档、标准、法规或项目主页
- 原始论文、数据集或代码仓库
- 权威媒体或行业机构
- 高质量二手分析
- 反例、争议和失败案例

针对每个子问题设计不同关键词，不只依赖一个搜索结果页面。

### 03 来源分级

按可信度区分：

- A：官方规范、原始数据、论文、源代码、监管文件
- B：权威媒体、专业机构、作者访谈
- C：社区讨论、博客、视频和经验帖

关键结论优先由 A 类来源支撑；C 类来源只能用于发现线索、案例或用户反馈。

### 04 事实核验

对关键事实检查：

1. 发布时间与事件发生时间是否一致。
2. 当前版本、价格、政策、人员和项目状态是否仍有效。
3. 不同来源是否引用同一个原始来源。
4. 数字的统计口径、样本、单位和时间范围是否一致。
5. 是否存在相反证据或限制条件。

### 05 形成结论

结论分为：

- 已确认事实
- 基于事实的推断
- 存在争议的判断
- 暂时无法确认的信息

为每项结论标注依据和置信度，不把推断写成事实。

### 06 输出决策建议

建议必须对应研究问题，并说明：

- 为什么推荐
- 适用条件
- 成本与风险
- 需要补充验证的事项

## rules

1. 时效性内容必须使用最新可用来源。
2. 技术问题优先使用官方文档、源代码和论文。
3. 不使用搜索结果摘要替代原文核实。
4. 不用星标数、下载量或营销文案单独证明质量。
5. 发现来源冲突时并列呈现，不强行统一。
6. 引用必须准确支撑对应句子。
7. 不编造无法找到的数据、参数或案例。

## output

- 结论摘要
- 研究范围和方法
- 分问题发现
- 证据与来源
- 争议、限制和置信度
- 可执行建议

## examples

### 开源项目选型调研

```text
调研可本地部署的代码关系图谱工具，用于分析 Java 和 Python 项目。

要求：
1. 先明确“关系图谱”需要覆盖调用关系、模块依赖、类关系还是运行时链路。
2. 优先核实项目官方仓库、文档、许可证、最近版本和维护状态。
3. 至少选择 5 个候选，比较语言支持、部署难度、输出效果、增量分析、资源需求和二次开发能力。
4. 区分静态分析、动态追踪和 LLM 辅助分析。
5. 给出适合内网部署的首选方案、备选方案和验证清单。
6. 对尚未实际运行验证的能力明确标注。
```
