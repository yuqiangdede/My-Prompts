# Codex 任务执行

## 目标

在当前可访问的代码仓库中完成一次明确的软件开发任务。任务完成的标准不是“给出建议”或“生成提示词”，而是：**读取真实代码 → 修改真实文件 → 执行可用验证 → 汇报可核验结果**。

## 输入

- 明确的实现、修改或修复目标
- 当前仓库/项目
- 技术栈与运行环境
- 不允许修改的范围
- 兼容性约束
- 验收标准
- 可用构建、测试、启动命令（如已知）

## workflow

### 01 建立任务边界

先从用户要求和仓库事实中确定：

- 最终行为要变成什么
- 哪些现有行为必须保持
- 可能受影响的模块、接口、数据和配置
- 是否允许新增依赖、迁移数据、修改公共协议或部署配置
- 哪些操作需要用户明确批准

对不会改变主方案的小缺口可以依据仓库惯例做最小合理处理；不要因次要信息缺失停在提问阶段。

### 02 仓库侦察

写代码前必须实际读取：

1. README / AGENTS.md / 项目规范。
2. 构建文件、模块结构和启动入口。
3. 与任务有关的类、函数、接口、数据模型、配置和测试。
4. 相关调用方与被调用方。
5. 当前实现中已经存在的相似模式。
6. 当前分支和用户已有未提交修改（工具环境可见时）。

只形成简短实施计划，然后继续执行，不停在计划阶段。

### 03 实施修改

- 按最小必要范围修改根因。
- 优先复用现有组件、接口、错误处理和编码风格。
- 涉及多文件时同步维护调用链、数据结构、状态语义、配置与测试。
- 不通过空 catch、默认成功、硬编码假数据、关闭校验等方式伪造成功。
- 不顺手扩大重构范围。

### 04 补充验证

根据项目实际能力执行尽可能接近生产行为的验证：

1. 格式化 / lint / 静态检查。
2. 目标单元或集成测试。
3. 受影响范围的回归测试。
4. 编译或构建。
5. 必要时启动最小服务或执行关键命令验证。

如果任务引入了可测试的新行为，应补测试；修复缺陷时优先增加能覆盖触发条件的回归测试。

### 05 失败闭环

验证失败时：

- 读取完整错误信息。
- 判断是本次改动、既有问题还是外部环境阻塞。
- 属于本次改动的问题继续修复并重新验证。
- 只有在缺少外部服务、权限、依赖、凭据或硬件等无法在当前环境解决时，才停止并明确阻塞证据。

### 06 最终复审

完成后检查：

- 是否满足用户原始验收目标。
- 是否误改无关行为。
- 接口/数据兼容性是否被破坏。
- 是否遗留临时文件、调试代码、硬编码路径或敏感信息。
- 测试结论是否和实际执行结果一致。

## rules

1. 不根据文件名猜实现，必须读取相关代码。
2. 不覆盖用户已有未提交修改。
3. 能执行就直接执行，不把“建议怎么改”当作完成。
4. 不声称测试、构建或启动通过，除非实际执行并获得成功结果。
5. 删除、数据库迁移、密钥、生产环境和不可逆操作需要明确检查点。
6. 不为了让测试通过而削弱真实业务校验。
7. 不要求展示隐藏思维过程；只保留计划、事实、操作、验证结果和风险。

## output

最终交付：

- 本次完成了什么
- 修改的文件及关键变化
- 实际执行的验证命令/测试
- 通过与失败结果
- 未能执行的验证及原因
- 兼容性/数据/部署影响
- 剩余风险或外部阻塞

## example

用户：

```text
在这个 Spring Boot 项目里给事件驳回接口增加 rejectReason，并保持旧客户端兼容。直接修改并跑测试。
```

正确行为：读取项目规范和相关调用链 → 修改 DTO/校验/服务/持久化或日志（按真实代码决定）→ 补回归测试 → 执行相关测试和构建 → 修复失败 → 汇报真实修改和验证结果。

错误行为：只输出一段“请让 Codex 按以下步骤修改”的提示词。
