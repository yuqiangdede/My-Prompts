# Codex 任务执行

## description

将自然语言开发需求整理成可直接交给 Codex CLI、Codex 桌面版或其他编码 Agent 的完整执行指令。强调先读仓库、再修改、自动验证、最后汇报，避免只给零散代码片段。

## input

- 目标仓库或项目目录
- 要实现、修改或修复的任务
- 技术栈与运行环境
- 不允许修改的范围
- 验收标准
- 可用命令、测试和部署方式

## workflow

### 01 建立任务边界

明确：

- 最终需要实现什么
- 哪些目录和接口允许修改
- 哪些行为必须保持兼容
- 是否允许新增依赖、迁移数据库或改配置

### 02 仓库侦察

要求 Codex 在写代码前完成：

1. 查看目录结构和项目说明。
2. 定位入口、核心模块、测试和配置。
3. 搜索相关类、接口、调用链和历史实现。
4. 识别当前分支、未提交修改和潜在冲突。
5. 给出简短实施计划，但不要停在计划阶段。

### 03 实施修改

按最小必要范围修改：

- 优先复用现有模块和编码风格。
- 同步处理接口、模型、配置、测试和文档。
- 不用临时绕过、假数据或吞异常掩盖问题。
- 涉及多文件时保持调用链、数据结构和异常语义一致。

### 04 验证闭环

依次执行：

1. 格式化和静态检查。
2. 目标模块测试。
3. 受影响范围回归测试。
4. 必要的构建或启动验证。
5. 检查日志、退出码和失败原因。

验证失败时继续定位并修复，直到通过或确认存在外部阻塞。

### 05 最终汇报

最终只汇报可核验信息：

- 修改了哪些文件
- 解决了什么问题
- 执行了哪些验证
- 哪些验证通过或未执行
- 仍有哪些风险和后续动作

## rules

1. 不根据文件名猜实现，必须先读取相关代码。
2. 不覆盖用户已有未提交修改。
3. 不擅自扩大重构范围。
4. 不把“建议怎么改”当作任务完成，能修改就直接修改。
5. 不声称测试通过，除非实际执行并看到成功结果。
6. 涉及删除、迁移、密钥、生产环境或不可逆操作时，必须设置明确检查点。
7. 不要求输出隐藏思维过程，只要求计划、证据、结果和风险。

## output

输出一个完整的 Codex 提示词，至少包含：

- 角色与目标
- 仓库侦察要求
- 实施约束
- 验证命令
- 验收标准
- 最终汇报格式

## examples

### Java 接口修改

```text
你正在修改一个现有 Java Spring Boot 项目。

任务：为事件处置接口增加“驳回原因”字段，并保持旧客户端兼容。

执行要求：
1. 先阅读 README、构建文件、事件相关 Controller、Service、DTO、数据库模型和测试。
2. 搜索现有状态流转和驳回逻辑，不要另起一套实现。
3. 给出简短计划后直接修改代码，不要停下来等待确认。
4. 旧请求未传驳回原因时仍可正常处理；新字段需要长度校验和清晰错误信息。
5. 同步补充单元测试或集成测试。
6. 执行项目现有格式检查、相关测试和构建命令。
7. 最终列出修改文件、验证结果、兼容性说明和剩余风险。

禁止：
- 修改无关模块；
- 引入未经必要性证明的新依赖；
- 用空 catch 或默认成功掩盖失败。
```
