# 代码审查与修复

## description

对现有代码进行证据驱动的审查，识别真实缺陷、兼容性风险、安全问题和可维护性问题，并在允许时直接完成修复和验证。

## input

- 仓库、分支、提交、PR 或代码目录
- 审查范围
- 业务目标和关键约束
- 运行环境与依赖
- 测试、构建和静态检查命令
- 是否允许直接修改代码

## workflow

### 01 理解变更目标

先读取任务说明、相关 Issue、PR 描述或业务需求，明确：

- 预期行为
- 不应改变的行为
- 输入输出边界
- 失败时应如何处理

### 02 建立影响面

检查：

- 调用方与被调用方
- 数据模型和状态流转
- 配置、缓存、并发和事务
- 权限、鉴权和敏感信息
- 测试覆盖和兼容性

### 03 分级发现问题

只报告可以从代码、测试或运行结果中证明的问题：

- P0：数据丢失、权限绕过、远程执行、生产不可用
- P1：核心功能错误、严重并发问题、明显兼容性破坏
- P2：边界条件、异常处理、性能退化、可维护性风险
- P3：非阻断改进

每个问题必须给出：位置、触发条件、影响、证据和修复方向。

### 04 直接修复

获得修改权限时：

1. 优先修复 P0/P1。
2. 按最小改动原则修复根因。
3. 为缺陷补充能够失败再通过的测试。
4. 不顺手重构无关代码。

### 05 验证

至少执行：

- 相关单元或集成测试
- 静态检查或编译
- 关键边界用例
- 对外接口兼容性检查

### 06 复审

修复后重新检查变更，确认没有引入新的空指针、竞态、异常吞噬、资源泄漏或行为漂移。

## rules

1. 不把个人风格偏好当作缺陷。
2. 不报告无法触发、无法定位或没有影响说明的问题。
3. 安全问题必须说明攻击前提和影响范围。
4. 性能问题优先用复杂度、查询计划、日志或基准结果支撑。
5. 未运行测试时必须明确写“未运行”。
6. 不泄露密钥、令牌、个人信息和生产数据。

## output

- 审查结论
- 按优先级排列的问题清单
- 已修复内容
- 验证结果
- 未解决风险

## examples

### 并发任务审查

```text
审查这个异步录像归档模块。重点检查：
- 同一事件是否会重复创建任务；
- 重试是否会造成重复文件或重复数据库记录；
- 状态更新是否具备原子性；
- 失败后是否能恢复；
- 清理任务是否可能删除仍在使用的文件。

先建立调用链和状态机，再报告有代码证据的问题。允许修改时直接修复 P0/P1，并补充并发或幂等测试。最终给出修改文件和实际执行的测试结果。
```
