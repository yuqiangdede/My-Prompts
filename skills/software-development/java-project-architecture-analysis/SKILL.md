# Java 项目架构分析

## description

对现有 Java 项目进行证据驱动的架构分析，建立从目录、构建依赖、启动入口、模块边界、调用链、数据模型到部署运行的完整视图。适用于 Spring Boot、Spring Cloud、传统 Servlet、Maven/Gradle 多模块项目以及逐步演进形成的遗留系统。

该 Skill 的目标不是根据目录名猜架构，也不是只输出技术栈清单，而是说明系统怎样启动、请求怎样流转、数据怎样变化、模块怎样依赖、风险集中在哪里，以及后续应如何修改。

## input

- Java 项目仓库或本地目录
- 分析目标：快速接手、功能定位、重构评估、故障排查、扩展设计或安全审计
- 关注的业务模块、接口、数据表或消息主题
- 构建与运行方式
- JDK、Maven/Gradle、Spring Boot/Cloud 等版本
- 数据库、中间件、对象存储和外部系统信息
- 是否允许执行构建、测试、启动和依赖分析命令
- 输出深度与时间范围

## workflow

### 01 建立分析边界

明确本次分析：

- 要回答的核心问题
- 需要覆盖的模块和调用链
- 是否只读分析，还是允许执行构建与测试
- 是否需要输出重构方案
- 哪些配置、密钥和生产信息不可读取或展示

如果目标不明确，优先围绕“系统如何运行、核心业务如何流转、当前最大风险是什么”建立默认分析范围。

### 02 仓库与构建侦察

读取并核对：

1. `README`、部署文档和开发说明。
2. `pom.xml`、父子模块关系、BOM、Profile 和插件。
3. `build.gradle`、`settings.gradle`、版本目录和任务配置。
4. JDK、Spring Boot、Spring Cloud、数据库驱动和关键依赖版本。
5. Dockerfile、Compose、Kubernetes、启动脚本和 CI 配置。
6. 配置文件、配置中心接入和环境变量占位符。

输出实际模块树，并区分：

- 可独立部署模块
- 公共库模块
- 领域或业务模块
- 基础设施适配模块
- 测试、脚本和文档模块

### 03 定位启动与装配机制

查找并说明：

- `main` 启动类和应用入口
- Spring 扫描范围
- 自动配置和条件装配
- Bean 定义、工厂、注册器和扩展点
- Filter、Interceptor、AOP、Listener 和定时任务
- 配置加载优先级
- 环境 Profile 对行为的影响

不能只列出类名，必须解释它们在启动和运行阶段的职责。

### 04 绘制模块依赖

建立模块和包级依赖关系：

- 谁依赖谁
- 依赖方向是否稳定
- 是否存在循环依赖
- 公共模块是否反向依赖业务模块
- Controller、Service、Domain、Repository、Client 等层次是否真实存在
- 包结构是按技术层、业务域还是混合方式组织

把依赖分成：

- 编译期依赖
- 运行期 Bean 依赖
- 数据库共享依赖
- 消息或接口依赖
- 配置和部署耦合

### 05 还原关键业务调用链

针对目标业务，从真实入口向下追踪：

```text
HTTP / 消息 / 定时任务 / 设备事件
  → 接入层
  → 参数校验与鉴权
  → 应用服务
  → 领域规则或状态流转
  → 数据访问 / 消息发送 / 外部接口
  → 事务提交
  → 响应、回调或异步结果
```

每条关键链路至少记录：

- 入口类和方法
- 核心 DTO、实体和枚举
- 状态变化
- 事务边界
- 同步与异步边界
- 异常处理
- 重试、幂等和补偿
- 外部依赖

### 06 分析数据与状态模型

核对：

- Entity、DO、PO、DTO、VO 是否混用
- 数据库表与对象映射
- 主键和业务唯一键
- 状态枚举及允许的状态迁移
- 乐观锁、版本号和并发控制
- 逻辑删除、审计字段和时间字段
- 缓存键和失效策略
- 数据库事务与消息一致性

当存在事件处置、任务执行、订单、审批、告警等流程时，必须画出状态机或状态迁移表。

### 07 分析接口与集成边界

整理：

- 对外 REST/RPC 接口
- 内部服务调用
- 消息队列生产与消费
- 文件、FTP、对象存储和流媒体交互
- 第三方 SDK 和硬件协议
- 超时、重试、限流、熔断和降级
- 接口版本与兼容策略

特别检查是否存在：

- Controller 直接操作数据库
- Service 跨越多个无关业务域
- 公共表被多个服务直接写入
- 异步消息没有幂等
- 外部调用处于长事务中
- 返回成功但后续步骤实际失败

### 08 分析非功能架构

从以下方面给出证据：

- 性能：热点链路、N+1 查询、大对象、锁和批量处理
- 可用性：单点、重试风暴、故障隔离和恢复方式
- 可扩展性：状态保存位置、定时任务竞争和水平扩容
- 可观测性：日志、Trace、Metric、审计和错误码
- 安全：认证、授权、数据范围、文件上传、反序列化和密钥管理
- 可测试性：单元测试、集成测试、测试容器和外部依赖替身
- 可维护性：重复代码、循环依赖、超大类、隐式约定和配置漂移

### 09 架构风险分级

按严重程度分类：

- P0：可能造成数据破坏、安全事故或系统整体不可用
- P1：核心链路高概率故障、数据不一致或无法扩容
- P2：明显增加修改成本、性能风险或运维复杂度
- P3：命名、结构和局部技术债

每个问题必须包含：

- 证据位置
- 触发条件
- 影响范围
- 当前行为
- 建议修改
- 验证方式

### 10 形成改造路线

不要直接建议“重写”。按成本和收益给出：

1. 立即修复项
2. 小范围结构调整
3. 中期模块解耦
4. 需要业务配合的数据或流程重构
5. 暂不修改但需要监控的风险

### Gate ① 架构证据完整性

在输出架构结论前，必须确认：

- 已读取真实构建文件和启动入口
- 已定位至少一条核心业务调用链
- 已区分代码事实、配置事实和推测
- 未仅根据文件夹命名判断分层

未通过时继续读取代码，不得输出确定性结论。

### Gate ② 数据与状态一致性

在提出改造方案前，必须确认：

- 事务边界已定位
- 状态迁移已核对
- 数据写入方和读取方已识别
- 异步链路的幂等和失败处理已检查

### Gate ③ 改造可执行性

建议必须说明：

- 修改范围
- 兼容性影响
- 数据迁移需求
- 测试和回滚方式
- 是否可以分阶段实施

## rules

1. 不根据常见 Spring 项目经验替代代码证据。
2. 不把包名或类名当作实际职责，必须阅读关键实现。
3. 不只输出依赖清单，必须还原业务链路和状态变化。
4. 不把所有问题归因于“架构不合理”，要指出具体触发机制。
5. 不建议为了形式上的分层增加无价值接口和对象转换。
6. 不默认微服务优于单体；根据团队、部署和业务边界判断。
7. 不忽略数据库、消息、配置和部署，它们都是架构的一部分。
8. 不声称命令或测试成功，除非实际执行并获得结果。
9. 涉及密钥、生产配置和个人信息时，只记录结构，不展示敏感值。
10. 最终结论必须区分：已验证、强推断、待验证。

## output

最终输出至少包含：

- 项目一句话定位
- 技术栈和版本摘要
- 模块树及模块职责
- 启动和装配流程
- 核心调用链
- 数据模型和状态机
- 外部集成关系
- 部署与运行结构
- P0–P3 风险清单
- 分阶段改造建议
- 未确认信息
- 建议继续阅读的关键文件

推荐附加图表：

- 模块依赖图
- 核心业务时序图
- 状态机图
- 部署图
- 数据流图

## examples

### 接手 Spring Boot 事件系统

```text
分析这个 Java Spring Boot 项目，目标是让新开发人员能够修改“预警指派、驳回、结案”流程。

执行要求：
1. 读取父子 pom、启动类、配置文件和部署脚本，输出真实模块树。
2. 从事件 Controller 开始追踪到 Service、状态校验、数据库写入、操作流水和消息推送。
3. 找出 PENDING、ASSIGNED、IGNORED、RESOLVED 等状态的定义和允许迁移。
4. 标注事务边界、并发更新、幂等、消息失败和回滚行为。
5. 检查 Web 与 APP 是否复用同一套状态规则。
6. 输出模块依赖图、状态机、关键调用链和 P0–P3 风险。
7. 给出保持现有接口兼容的分阶段改造方案。

禁止只根据目录名总结；每项关键结论都要给出文件和类的证据位置。
```
