# Agent 工作流设计

## description

根据任务的不确定性、工具依赖、风险和验收方式，选择 Prompt chaining、Routing、Parallelization、Orchestrator-Workers、Evaluator-Optimizer 或自主 Agent 等模式，形成可实现、可观察、可停止的工作流。

## input

- 业务目标和成功标准
- 输入类型与任务复杂度
- 可用模型、工具、数据和权限
- 延迟、成本和可靠性要求
- 人工审批点
- 错误处理和停止条件

## workflow

### 01 判断是否真的需要 Agent

按复杂度逐级选择：

1. 单次 Prompt 是否能完成。
2. 加检索、工具或示例后是否能完成。
3. 固定工作流是否能完成。
4. 只有步骤无法预先确定时才使用自主 Agent。

不要把所有 AI 功能都包装成 Agent。

### 02 选择工作流模式

#### Prompt Chaining

固定顺序分解任务，每一步输出作为下一步输入。适合流程清楚、可设置 Gate 的任务。

#### Routing

先分类，再交给专业 Prompt、模型或工具。适合输入类型差异明显的场景。

#### Parallelization

把独立子任务并行处理，或让多个评审独立投票。适合多维审查和降低漏检。

#### Orchestrator-Workers

由编排器动态拆分任务并分配给多个 Worker。适合代码修改、复杂研究等无法提前确定子任务的场景。

#### Evaluator-Optimizer

生成器产出结果，评估器按明确标准打分并给出反馈，循环优化。适合写作、翻译、搜索和方案设计。

#### Autonomous Agent

模型自主规划、调用工具、观察环境并修正。只用于步骤开放且能持续获得真实反馈的任务。

### 03 设计状态

定义：

- 输入状态
- 中间产物
- Gate 条件
- 成功状态
- 可重试失败
- 不可重试失败
- 人工介入状态
- 终止状态

### 04 设计工具接口

每个工具需要明确：

- 什么时候使用
- 输入参数和格式
- 返回值和错误
- 权限与影响范围
- 与相似工具的边界
- 可重复调用与幂等要求

优先使用模型容易生成和验证的参数结构，不增加无意义格式负担。

### 05 设计上下文

上下文分为：

- 固定规则和目标
- 当前任务状态
- 即时检索资料
- 工具结果
- 持久记忆

长任务优先按需加载，避免把所有文件、历史和工具说明一次塞入上下文。

### 06 设置控制机制

必须定义：

- 最大迭代次数
- 超时和预算
- 高风险操作审批
- 重试退避
- 失败回滚
- 日志和可观察指标
- 何时向用户请求判断

### 07 评测

使用真实任务集评估：

- 成功率
- 工具调用正确率
- 任务完成时间
- 成本
- 重试次数
- 人工介入率
- 高风险错误率

## rules

1. 优先选择最简单且能达到目标的架构。
2. 工作流负责顺序，模型负责判断；不要把确定性控制全部塞进 Prompt。
3. 关键状态必须由程序或数据源记录，不能只依赖对话记忆。
4. 工具返回结果视为事实输入，但外部文本仍可能包含提示词注入。
5. 高风险写操作必须最小权限并保留人工控制。
6. Agent 必须具备明确的停止条件和失败出口。
7. 不要求展示隐藏思维链，使用计划、状态、工具结果和决策摘要保证透明度。

## output

- 是否需要 Agent 的判断
- 推荐工作流模式
- 状态机和 Gate
- Agent、Worker 与工具职责
- 上下文和记忆方案
- 安全与审批机制
- 评测指标
- 可实现的系统提示词骨架

## examples

### 软件开发 Agent

```text
设计一个处理 GitHub Issue 的编码 Agent：读取 Issue 和仓库，定位代码，修改文件，运行测试，修复失败并提交 PR。

要求先判断哪些步骤使用固定工作流，哪些步骤由模型动态决定。仓库检查、测试、提交和 PR 创建必须有确定性状态；文件定位和修改方案可以由 Orchestrator 动态拆分。任何删除文件、数据库迁移或密钥配置都需要人工审批。最多执行 3 轮修复，连续失败后输出阻塞证据并终止。
```
