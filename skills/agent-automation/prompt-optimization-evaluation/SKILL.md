# 提示词优化与评测

## description

通过测试集、评价维度、基线、失败归因和回归测试优化 Prompt 或 Skill。目标不是让提示词看起来更复杂，而是让目标任务的成功率、稳定性和可维护性实际提高。

## input

- 当前 Prompt、Skill 或系统提示词
- 目标任务与用户群
- 代表性输入样本
- 期望输出或验收规则
- 使用的模型和参数
- 成本、延迟和格式约束

## workflow

### 01 定义成功

把“回答更好”转化为可检查指标，例如：

- 事实正确
- 覆盖完整
- 格式合法
- 约束遵守
- 工具选择正确
- 任务真正完成
- 无危险副作用

区分硬性失败和质量偏好。

### 02 建立测试集

测试集至少包含：

- 正常样本
- 边界样本
- 模糊输入
- 冲突指令
- 长上下文
- 工具失败
- 恶意或注入内容
- 历史真实失败样本

不要只用一个成功案例反复调 Prompt。

### 03 建立基线

固定：

- 模型版本
- 系统提示词
- 工具说明
- 温度等参数
- 测试输入
- 评分规则

运行当前版本并记录基线结果。

### 04 归因失败

失败原因分为：

- 任务定义不清
- 上下文缺失或污染
- 指令优先级冲突
- 输出格式困难
- 工具接口不清
- 模型能力不足
- 流程或代码问题
- 评价标准本身有问题

先修根因，不用增加更多形容词掩盖问题。

### 05 设计候选版本

每次只改变一个主要因素：

- 指令顺序
- 结构和分隔符
- 示例
- 输出 schema
- 工作流拆分
- 工具描述
- Gate 和自检

保留版本号和变更说明。

### 06 运行评测

采用组合评价：

- 代码或规则校验：JSON、字段、编译、测试、关键词和长度
- 人工评价：事实、逻辑、可用性和语气
- 模型评价：按固定 rubric 评分，并抽样人工复核
- 环境评价：工具调用和最终状态是否正确

### 07 回归与发布

新版本只有在目标指标改善且关键样本不退化时发布。记录：

- 总体变化
- 分类型变化
- 新增失败
- 成本与延迟变化
- 已知限制

## rules

1. 不用“感觉更好”代替评测。
2. 测试集与提示词开发样本应适当分离，避免过拟合。
3. 不用模型自评分作为唯一证据。
4. 评测失败时先检查任务和评分定义。
5. 对非确定性输出运行多次，观察波动而不是只选最好结果。
6. 复杂 Prompt 若无指标收益，应回退到更简单版本。
7. 保存失败样本，作为后续回归集。

## output

- 成功标准和评分表
- 测试集设计
- 当前基线
- 失败归因
- 候选 Prompt
- 对比结果
- 发布或回退建议

## examples

### 技术调研 Prompt 评测

```text
优化一个“开源项目调研”提示词。建立 20 个测试任务，覆盖热门项目、冷门项目、停止维护项目、许可证冲突、无官方文档和搜索结果相互矛盾等情况。

评分维度：
- 是否使用官方来源；
- 是否核对当前版本和维护状态；
- 是否区分事实与推断；
- 是否给出适用条件和风险；
- 是否编造参数；
- 引用是否支撑结论。

先运行当前 Prompt 建立基线，再分别测试“增加来源分级”“增加事实核验 Gate”“增加固定报告模板”三个候选版本。一次只改变一个主要变量，输出逐项对比和回归样本。
```
