# 从零生成 HTML 高保真原型 Skill

## 目标

根据用户提供的需求、PRD、业务流程或产品想法，从零创建一套：

- 可以在浏览器运行。
- 页面风格统一。
- 核心流程可点击。
- 模拟数据真实可信。
- 可以用于业务演示和需求评审。
- 后续容易继续修改和扩展。

的 HTML 高保真原型。

本 Skill 的目标不是生成一张网页截图，而是生成一套真正可以运行、点击和演示的前端原型项目。

## 适用场景

当用户提出以下需求时，使用本 Skill：

- 根据 PRD 生成高保真 HTML 原型。
- 根据需求分析结果生成产品 Demo。
- 从零搭建后台管理系统原型。
- 创建可点击的 SaaS、CRM、运营后台或业务工作台。
- 创建 PC 端或移动端 Web 原型。
- 将业务流程转成多页面可演示原型。
- 在没有现成前端项目的情况下快速生成 Demo。
- 暂时不开发后端，只通过模拟数据验证产品结构和交互。

## 不适用场景

以下情况不默认使用本 Skill：

- 用户已经有现成前端项目，只需要新增或修改页面。
- 用户只需要一张静态效果图。
- 用户只需要营销官网或落地页。
- 用户要求开发后端、数据库或生产服务。
- 用户只需要技术架构文档。
- 用户当前需求仍然非常模糊。
- 用户只需要 PRD 或需求分析。

处理原则：

- 已有前端项目：使用“在已有项目上画高保真原型 Skill”。
- 需求仍模糊：先进行需求澄清或需求分析。
- 需要完整产品文档：先使用 PRD Skill。
- 只需要视觉图片：使用图像生成或设计工具。

## 调用前提

开始生成原型前，至少应基本明确：

- 产品目标。
- 目标用户或角色。
- 核心业务场景。
- 核心用户任务。
- 主要页面。
- 页面之间的关系。
- 关键字段和状态。
- 关键操作。
- 本期产品范围。

如果缺失信息会直接影响产品结构，应先澄清。

如果只是展示层细节缺失，可以使用合理假设，但必须在最终回复中说明。

## 核心原则

### 1. 先拆产品，再写代码

先提取：

- 产品名称。
- 产品目标。
- 用户角色。
- 核心任务。
- 页面清单。
- 页面层级。
- 导航结构。
- 页面跳转关系。
- 业务字段。
- 业务状态。
- 权限差异。
- 关键交互。
- 待确认规则。

### 2. 根据复杂度选择技术方案

#### 单文件 HTML

适合单页面工具、简单业务演示、少量交互，以及希望双击文件直接打开的场景。

#### HTML、CSS、JavaScript 多文件项目

适合多页面系统、页面跳转、表单、列表、弹窗和本地状态交互。

#### React 或 Vue 项目

适合页面较多、组件复用明显、状态交互复杂，或未来可能继续进入开发的项目。

选择原则：

> 能用简单方式完成，就不要为了显得专业而引入复杂框架。

### 3. 先建立统一设计系统

先定义：

- 主色和辅助色。
- 页面背景色。
- 字体和字号层级。
- 页面间距。
- 圆角。
- 按钮样式。
- 表单样式。
- 表格密度。
- 状态颜色。
- 图标风格。
- 弹窗和消息样式。
- 页面布局方式。

### 4. 页面围绕用户任务设计

每个页面都应明确：

- 谁使用。
- 为什么进入。
- 主要完成什么任务。
- 需要看到什么信息。
- 需要执行什么操作。
- 完成后去哪里。

### 5. 核心流程必须可以点击

至少实现一条完整业务流程，并支持：

- 页面跳转。
- 搜索。
- 筛选。
- Tab 切换。
- 弹窗和抽屉。
- 表单填写。
- 表单校验。
- 新增和编辑。
- 删除或关闭。
- 状态切换。
- 成功与失败反馈。
- 二次确认。
- 模拟数据更新。

### 6. 使用真实感模拟数据

避免使用 Test User、Lorem ipsum、Company A、Sample Data、User 001。

模拟数据应覆盖：

- 不同状态。
- 不同角色。
- 长文本。
- 缺失值。
- 异常记录。
- 警告信息。
- 边界数据。
- 空结果。
- 禁用操作。
- 不同业务阶段。

### 7. 不擅自扩大产品范围

AI 可以补充展示层细节，但不得擅自增加：

- 新业务模块。
- 新角色权限。
- 新状态流转。
- 新审批规则。
- 新业务计算方式。
- 新外部系统依赖。
- 与核心需求无关的管理能力。

必要假设必须在最终回复中集中说明。

## 编码前分析

开始编码前，整理：

- 产品目标。
- 用户角色。
- 核心场景。
- 核心任务。
- 页面清单。
- 页面层级。
- 导航结构。
- 页面目标。
- 页面跳转关系。
- 关键字段。
- 关键状态。
- 权限差异。
- 关键交互。
- 模拟数据需求。
- 产品假设。
- 待确认规则。

## 页面架构输出

编码前先形成页面架构。

示例：

```text
客户跟进系统

├── 登录页
├── 工作台
├── 客户管理
│   ├── 客户列表
│   ├── 客户详情
│   └── 新建客户
├── 跟进管理
│   ├── 跟进任务
│   └── 新增跟进
└── 个人中心
```

每个页面至少说明：

- 页面目标。
- 使用角色。
- 核心内容。
- 主要操作。
- 跳转页面。
- 关键状态。

## 视觉规范

### 后台系统

默认采用：

- 左侧导航加顶部工具栏。
- 浅灰页面背景。
- 白色内容区域。
- 明确的品牌主色。
- 稳定的信息密度。
- 轻圆角。
- 弱阴影。
- 清晰表格和表单。
- 高识别度状态标签。

避免：

- 巨大首屏标题。
- 营销式 Hero 区域。
- 大量装饰性渐变。
- 漂浮光球。
- 纯氛围背景。
- 每个区块都做成卡片。
- 卡片嵌套卡片。
- 过度留白导致信息密度过低。

### 移动端

如果用户明确要求移动端：

- 采用移动优先布局。
- 保证点击区域足够大。
- 处理键盘和表单。
- 避免固定元素遮挡。
- 检查安全间距。
- 确保关键操作始终可达。

## 实现流程

### 第一步：读取需求材料

提取产品目标、用户角色、核心场景、页面、字段、状态、操作、权限、跳转和待确认规则。

### 第二步：输出页面架构

明确页面清单、层级、导航和跳转关系。

### 第三步：选择技术方案

从以下方案中选择：

- 单文件 HTML。
- HTML、CSS、JavaScript 多文件项目。
- React 项目。
- Vue 项目。

说明选择理由。

### 第四步：建立视觉规范

统一颜色、字体、间距、圆角、控件、状态、图标和页面布局。

### 第五步：搭建公共框架

创建：

- 导航。
- 页面容器。
- 公共样式。
- 公共组件。
- 表单样式。
- 表格样式。
- 弹窗。
- 抽屉。
- 消息提示。
- 模拟数据。

### 第六步：逐页实现

每个页面至少包含：

- 页面标题。
- 页面目标。
- 核心信息。
- 主要操作。
- 默认状态。
- 空状态。
- 加载状态。
- 错误状态。
- 页面跳转。
- 权限限制。

### 第七步：补充交互

实现搜索、筛选、排序、Tab、新增、编辑、删除、状态变化、表单校验、成功和失败反馈、二次确认和数据更新。

### 第八步：完整走查

检查：

- 页面能否进入。
- 按钮是否有反应。
- 跳转是否正确。
- 数据是否更新。
- 操作是否有反馈。
- 页面是否存在死路。
- 页面风格是否统一。
- 文字是否溢出。
- 弹窗和抽屉是否可用。
- 小屏是否严重错位。

### 第九步：输出运行说明

说明：

- 项目目录结构。
- 使用的技术方案。
- 入口文件。
- 如何本地运行。
- 哪些流程可以演示。
- 哪些数据是模拟数据。
- 哪些规则属于产品假设。
- 哪些内容仍待确认。

## 页面状态标准

根据实际需要补充：

- 默认状态。
- 加载状态。
- 有数据状态。
- 无数据状态。
- 搜索无结果。
- 表单填写状态。
- 校验错误状态。
- 提交中状态。
- 提交成功状态。
- 提交失败状态。
- 禁用状态。
- 无权限状态。
- 数据已失效状态。
- 网络异常状态。

## 交互标准

每个关键操作都应明确：

- 什么情况下展示。
- 什么情况下可点击。
- 什么情况下禁用。
- 点击前是否校验。
- 是否需要二次确认。
- 点击中是否禁止重复操作。
- 成功后发生什么。
- 失败后如何反馈。
- 是否更新本地模拟数据。
- 是否跳转或返回。

## 目录结构建议

### 单文件 HTML

```text
prototype/
└── index.html
```

### 多文件 HTML 项目

```text
prototype/
├── index.html
├── pages/
├── assets/
├── css/
├── js/
├── mock/
└── README.md
```

### React 或 Vue 项目

沿用框架标准目录，并保证页面和组件分层清晰、模拟数据容易修改、路由关系明确，不引入无必要复杂架构。

## 最终交付物

最终应包括：

- 可运行的前端项目。
- 页面和路由。
- 公共样式。
- 可复用组件。
- 真实感模拟数据。
- 可点击核心流程。
- 页面状态。
- 表单校验。
- 成功和错误反馈。
- 本地运行说明。
- 产品假设清单。
- 待确认规则清单。

## 完成标准

满足以下条件后，原型才算完成：

- 页面结构符合需求。
- 视觉风格统一。
- 核心用户流程可以完整走通。
- 所有主要操作都有明确反馈。
- 页面之间没有死路。
- 关键操作后模拟数据能够更新。
- 必要页面状态已经体现。
- 文字没有明显溢出。
- 页面在目标设备上可正常使用。
- 项目可以本地运行，没有阻塞错误。
- 没有擅自扩大产品范围。
- 产品假设和待确认规则已经说明。

最终至少达到：

### 可以看

视觉完整，接近真实产品。

### 可以点

按钮、筛选、表单和跳转可以正常操作。

### 可以讲

产品经理可以直接用于业务演示、需求评审和方案沟通。

## 最终回复要求

完成后说明：

- 创建了哪些页面和模块。
- 核心流程如何演示。
- 哪些交互已经可以点击。
- 使用了哪些模拟数据。
- 选择了什么技术方案。
- 做出了哪些产品假设。
- 哪些业务规则仍待确认。
- 项目如何运行和预览。
- 完成了哪些视觉和交互检查。
