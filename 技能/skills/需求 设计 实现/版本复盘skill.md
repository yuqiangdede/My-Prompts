# 版本复盘 Skill

## 一、目标

对已经完成开发、上线或阶段性交付的产品版本进行结构化复盘。

最终回答：

- 当初为什么做这个版本。
- 目标有没有达到。
- 哪些结果符合预期。
- 哪些结果没有达到预期。
- 哪些过程做得好。
- 哪些地方产生了返工、延迟或风险。
- 问题为什么发生。
- 哪些属于偶发问题。
- 哪些属于系统性问题。
- 哪些做法值得继续保留。
- 哪些做法应该停止。
- 下一次具体应该改变什么。
- 哪些经验可以沉淀成可复用方法。

核心原则：

> 复盘不是回忆发生了什么，而是把一次项目经历转化成下一次可以直接复用的方法。

## 二、适用场景

当用户提出以下需求时，使用本 Skill：

- 复盘一个已经上线的产品版本。
- 复盘一个项目阶段。
- 分析版本为什么没有达到目标。
- 总结本次项目的问题和经验。
- 将项目经验沉淀成下一次可复用的方法。
- 根据版本目标、过程和数据生成复盘报告。
- 将复盘问题转化成 Checklist、SOP、模板或 Skill。
- 判断哪些问题属于流程问题、人员问题、需求问题或方法问题。
- 对需求、开发、测试、上线全过程进行回顾。

## 三、不适用场景

以下情况不默认使用本 Skill：

- 用户还在需求澄清阶段。
- 用户只需要写 PRD。
- 用户只需要做需求评审。
- 用户只需要分析上线后的数据，不需要过程复盘。
- 用户只需要项目周报或项目汇报。
- 用户只需要会议纪要。
- 用户只需要单个 Bug 的原因分析。

处理原则：

- 需求仍未明确：先进行需求澄清或需求分析。
- 只分析上线效果：优先使用“上线后数据分析 Skill”。
- 只分析一个具体问题：直接做专项根因分析。
- 项目尚未形成足够过程和结果信息：先说明当前只能做阶段性复盘。

## 四、复盘材料

开始复盘时，优先读取现有材料，包括：

- 原始需求。
- 需求分析。
- PRD。
- 产品方案。
- 原型。
- 项目计划。
- 需求变更记录。
- 需求评审记录。
- 技术方案。
- 开发过程记录。
- 测试问题。
- Bug 清单。
- 上线记录。
- 上线后数据。
- 用户反馈。
- 业务反馈。
- 项目沟通记录。
- 风险记录。
- 关键决策记录。

如果用户已经提供材料，不要重复要求用户提供相同信息。

如果材料不完整，明确区分：

- 已确认事实。
- 合理判断。
- 待确认信息。

不要把推测写成事实。

## 五、核心原则

### 1. 先回到目标，再看过程

复盘首先回答：

- 当初为什么做这个版本。
- 希望解决什么问题。
- 目标用户是谁。
- 核心目标是什么。
- 成功标准是什么。
- 上线前基线是什么。
- 实际结果是什么。

不要从“这个版本做了哪些功能”开始。

### 2. 区分结果复盘和过程复盘

结果复盘关注：

- 产品目标是否达到。
- 核心指标是否改善。
- 用户是否使用。
- 业务是否获得价值。
- 结果是否符合预期。
- 哪些结果当前还不能判断。

过程复盘关注：

- 需求是否清晰。
- 方案是否反复变化。
- 评审是否有效。
- 是否出现开发返工。
- 测试时间是否被压缩。
- 上线是否出现风险。
- 跨团队协作是否顺畅。
- 关键问题是否被提前发现。

### 3. 不停留在问题现象

不要把“开发过程中频繁修改需求”“沟通不到位”“考虑不充分”直接当成最终根因。

继续分析：

- 为什么发生。
- 哪些规则没有提前确认。
- 哪些问题是在开发阶段才暴露。
- 是否缺少关键角色参与。
- 是否存在技术限制后置发现。
- 是否存在范围失控。

### 4. 区分偶发问题和系统性问题

偶发问题例如：

- 某个关键成员临时请假。
- 外部系统短期不可用。
- 临时政策调整。

系统性问题例如：

- 业务规则总是在开发阶段补。
- PRD 和原型经常不一致。
- 每次测试时间都被压缩。
- 上线后才发现没有埋点。
- 需求范围经常不断膨胀。
- 相同问题在多个项目中重复出现。

系统性问题必须优先形成机制性改进。

### 5. 不只找问题，也要识别有效做法

识别：

- 哪些方法有效。
- 哪些机制降低了风险。
- 哪些工具提高了效率。
- 哪些做法减少了返工。
- 哪些动作帮助目标更快达成。

这些内容进入 Continue 清单。

### 6. 经验必须转化成动作

避免输出：

- 加强沟通。
- 提前规划。
- 提高需求质量。
- 增强数据意识。
- 提高评审效率。

改进动作必须尽量明确：

- 改什么。
- 在什么阶段执行。
- 谁负责。
- 什么情况下触发。
- 输出什么结果。
- 如何判断已经执行。

### 7. 复盘产物不能只是一篇文档

真正有价值的复盘应继续沉淀成：

- Checklist。
- 模板。
- SOP。
- 规则。
- Skill。
- 项目规范。
- 评审标准。
- 决策原则。

## 六、复盘分析框架

### 1. 目标复盘

回答：

- 本次版本目标是什么。
- 为什么要做。
- 成功标准是什么。
- 实际结果是什么。
- 哪些目标达成。
- 哪些目标部分达成。
- 哪些目标未达成。
- 哪些目前无法判断。

### 2. 结果复盘

建议至少分析：

- 核心指标。
- 上线前基线。
- 上线后表现。
- 目标值。
- 用户反馈。
- 业务反馈。
- 异常数据。
- 是否存在归因不确定性。

### 3. 过程复盘

按照项目阶段检查：

需求 → 分析 → 方案 → 评审 → 开发 → 测试 → 上线 → 数据观察

每个阶段识别：

- 发生了什么。
- 是否按计划完成。
- 是否出现返工。
- 是否发生变更。
- 是否出现延期。
- 是否产生风险。
- 是否有关键决策。

### 4. 问题根因分析

可以使用：

- 5 Why。
- 人 / 流程 / 工具 / 规则 / 数据 / 组织。
- 时间线回溯。
- 决策节点分析。
- 输入-过程-结果分析。

禁止把“沟通不到位”“考虑不充分”直接当成最终根因。

### 5. 有效做法分析

识别：

- 哪些做法有效。
- 为什么有效。
- 适合什么场景。
- 下次是否继续使用。
- 是否可以模板化或 Skill 化。

### 6. 系统性问题识别

判断：

- 这个问题是否曾发生过。
- 是否会在下一次重复。
- 是否来自现有流程缺陷。
- 是否需要机制性改变。
- 是否适合加入固定检查清单。

## 七、Continue / Stop / Start

### Continue：继续做

已经证明有效的做法，例如：

- 复杂需求先做高保真 Demo。
- 需求评审前先做 AI 自检。
- 上线后一周固定看核心指标。
- 重要规则使用表格集中确认。

### Stop：停止做

已经证明低效、容易产生风险或没有价值的做法，例如：

- 需求规则不清楚就直接进入开发。
- 为赶时间跳过关键业务方评审。
- PRD 和原型分开维护但不做版本同步。
- 上线后只看 PV 和 UV。

### Start：开始做

下一次必须新增的机制或动作，例如：

- PRD 强制增加状态流转。
- 开发前检查埋点方案。
- 复杂业务先灰度再全量。
- 需求评审增加异常和边界检查。
- 每个版本结束后沉淀 Checklist。

## 八、改进动作标准

每个重要问题至少生成一条明确改进动作。

推荐格式：

```text
问题：
根因：
问题类型：
改进动作：
执行阶段：
责任角色：
触发条件：
完成标准：
沉淀方式：
```

## 九、执行流程

### 第一步：读取版本材料

整理：

- 原始目标。
- 版本范围。
- 关键过程。
- 变更。
- 问题。
- 数据。
- 用户反馈。
- 最终结果。

### 第二步：回顾版本目标

明确：

- 为什么做。
- 核心目标。
- 成功标准。
- 实际结果。

### 第三步：复盘结果

判断：

- 达成。
- 部分达成。
- 未达成。
- 暂无法判断。

说明原因和证据。

### 第四步：复盘过程

按照项目生命周期还原关键事件。

### 第五步：识别关键问题

优先关注：

- 返工。
- 延期。
- 频繁变更。
- 风险遗漏。
- 信息不一致。
- 决策反复。
- 数据缺失。
- 用户反馈集中问题。

### 第六步：分析根因

对关键问题继续追问，不停留在表面现象。

### 第七步：识别有效做法

找出本次值得保留的方法。

### 第八步：识别系统性问题

判断哪些问题下次大概率还会再次发生。

### 第九步：生成改进动作

将每个重要结论转化成可执行动作。

### 第十步：沉淀可复用经验

将经验转化成：

- Checklist。
- 模板。
- SOP。
- Skill。
- 规则。
- 项目规范。

## 十、最终输出结构

### 1. 版本基本信息

- 版本名称。
- 上线时间。
- 复盘时间。
- 参与角色。
- 版本范围。

### 2. 版本目标

- 产品目标。
- 用户目标。
- 核心指标。
- 成功标准。

### 3. 结果复盘

- 上线前基线。
- 上线后结果。
- 目标达成情况。
- 用户反馈。
- 业务反馈。

### 4. 过程复盘

按阶段说明：

- 做得好的地方。
- 发生的问题。
- 关键变更。
- 风险。
- 关键决策。

### 5. 关键问题与根因

每个问题说明：

- 问题现象。
- 根因。
- 影响。
- 问题类型。
- 是否会重复发生。

### 6. Continue

继续保留的有效做法。

### 7. Stop

应该停止的低效或高风险做法。

### 8. Start

下一次必须新增的机制或动作。

### 9. 改进动作清单

明确：

- 动作。
- 阶段。
- 责任角色。
- 完成标准。

### 10. 可沉淀资产

判断哪些内容可以沉淀为：

- Skill。
- Checklist。
- 模板。
- SOP。
- 规则。
- 项目规范。

## 十一、完成标准

版本复盘只有满足以下条件才算完成：

- 明确回到了原始目标。
- 区分了结果问题和过程问题。
- 没有把问题现象直接当成根因。
- 至少识别出关键成功经验。
- 识别出系统性问题。
- 重要问题都有明确改进动作。
- 改进动作可以执行和验证。
- 输出 Continue / Stop / Start。
- 至少有一部分经验可以沉淀为可复用资产。
- 最终结论能够影响下一次项目，而不只是记录过去。

## 十二、最终回复要求

最终回复应保持产品经理容易理解的表达方式，重点说明：

- 这次版本目标是否达成。
- 哪些事情做对了。
- 哪些事情出了问题。
- 问题为什么发生。
- 哪些问题下次可能再次出现。
- 下一次具体要改变什么。
- 哪些经验可以固化进现有 Skill、模板或流程。

避免空泛总结。

最终复盘应让用户能够直接拿去：

- 做项目复盘会。
- 发给团队。
- 沉淀进知识库。
- 修改现有 Skill。
- 建立下一次项目检查清单。
