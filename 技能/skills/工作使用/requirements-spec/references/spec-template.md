# 标准结构与用例字段

## 章节结构

用户格式优先；无模板采用以下结构，可按实际内容调整，避免空章节。

1. 产品概述：产品定位、产品范围、编写目的、术语、描述约定。
2. 总体描述：业务目标、角色、项目范围、裁剪、环境及依赖。
3. 功能需求：目录，按业务模块分组的具体用例；各来源融合后的需求并列编排，基线、定制改动和新增功能体现为用例属性。
4. 外部接口需求：方向、数据、动作、错误及协议边界。
5. 数据与业务规则：状态、单位、公式、唯一性及生命周期。
6. 非功能需求：性能、安全、故障隔离、兼容、审计、留存。
7. 验收要求：范围、场景和关键边界。
8. 待确认清单：仅当人工选择保留时包含。

文档属性只填已知项目、版本、日期和范围；不编造作者、批准或合同信息。整体产品范围与当前项目详细需求分别表述。附图表示整体能力时说明哪些纳入项目。

## 统一用例表格

以下右栏是编制要求，不得原样作为未填写的交付内容。

| 项目 | 描述要求 |
| --- | --- |
| 需求编号 | 唯一且稳定，沿用用户或现有项目编号 |
| 需求名称 | 用户目标或产品提供的独立业务能力，避免以组件或类名命名 |
| 需求来源分类 | 基线 / 有定制改动 / 全新定制功能 |
| 功能说明 | 用户在业务场景中遇到的问题、需要解决的目标，以及产品提供的能力与结果 |
| 优先级 | 高 / 中 / 低，已有明确优先级优先 |
| 功能入口 | 菜单/按钮路径，或消息、接口、任务触发源 |
| 部件说明 | 按需说明用户可见的布局、字段、列表、弹窗、按钮、图表；只保留理解操作或验收所需的细节，有图时关联图号，不列内部组件职责 |
| 参与者 | 业务岗位、授权账号或外部系统 |
| 前置条件 | 权限、配置、数据及业务状态 |
| 后置条件 | 成功后的状态、数据、通知和结果；只读功能说明不改变数据 |
| 正常过程 | N0010 等描述操作和响应，多场景可用 N1/N2 |
| 可选过程 | A0010 等描述分支、取消、替代或恢复；不存在写无 |
| 异常过程 | E0010 等说明失败条件、提示、重试、保留或回滚 |
| 特殊需求 | 专属性能、安全、兼容、实时要求或引用共用规则 |
| 附加说明 | 单位、公式、数据来源、限制和业务边界 |
| 验收要点 | 可观察、可验证的正常及边界结果 |

Markdown 表格中多步骤以 <br> 分隔；HTML/Word 转换为真实段落。业务协议字段可在需要时保留，代码类名和源码位置不进入业务入口。

## 两种待确认模式

**保留模式**：相关字段使用“待确认：…”说明真实缺口，末尾列编号、问题、影响需求及可选方案。正式措辞仍去掉“拟定”“源码推导”等编制痕迹。没有缺口的字段不滥用待确认。

**最可能方案模式**：把待确认问题逐一解决为明确描述，删除清单和标记。优先沿用最新修订与实际业务交互；在工作笔记记录假设和理由。不能为了去掉标记而删除整个需求或忽略问题。

## 工作笔记

证据路径、分类理由、需求覆盖表、冲突决策、默认假设及检查结果保存在任务允许的草稿或临时位置。正文只保留业务规格；内部笔记默认不交付。

## 容易混淆的边界

- 图片数、子事件数、聚合预警数、设备数不能混用；多图不自动增加事件量。
- 人员编码与登录账号编码不是同一概念，授权和负责人映射需明确。
- 资源展示、事件查询、预警生成、自动联动是不同能力；裁剪时逐项处理。
- “无须输入 KEY”与“KEY 必填”按有效增量修订统一，异常过程与验收同步调整。
- 参考文档的“无法测试”不是业务限制，应转换为明确条件与验收方法；实际测试证据另行记录。
