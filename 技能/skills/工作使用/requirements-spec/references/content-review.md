# 内容校审和读者检查

方法来源：[Anthropic doc-coauthoring](https://github.com/anthropics/skills/blob/main/skills/doc-coauthoring/SKILL.md)。

此处按需求规格书适配 Context Gathering、Refinement & Structure、Reader Testing 三阶段；不是原文全文复制，也不依赖 Claude 专有工具。用户要求使用上游原 Skill 时读取当前版本。它负责内容校审，不生成 Word 文件。

## 上下文整理

整理项目、受众、模板、范围、裁剪及用户已作的选择。已有文档直接作为输入，不重复已结束的访谈。核对可选参考文档是否作为内容来源或样式模板，避免误用示例为项目事实。

完成条件：关键概念、适用范围和人工选择均明确；真实缺口已按用户选择保留或形成方案。

## 结构迭代

逐项检查：
- 每个输入功能与增量裁剪条目都有归属。
- 参考需求、源码推导需求和 docs/ADR 需求已按 SKILL.md 的统一需求池规则处理，输入映射完整，重复已合并，互补规则和有效验收条件无遗漏。
- 需求目录与正文编号一致；所有需求按业务模块并列组织，没有按材料来源分开粘贴的章节或附录，也没有同一业务的重复用例。
- 需求名称与功能说明体现用户场景、待解决问题、业务目标和产品能力；需求边界按独立业务目标确定，组件实现细节仅在操作、约束或验收需要时保留。
- 入口、权限、前后状态、流程与验收一致。
- 取消、幂等、并发、无数据、无权限及依赖失败按适用性覆盖。
- 统计单位、公式、时间窗、时区和限制可验证。
- 裁剪同步修改依赖入口、工具、通知、统计和验收。
- 来源分类不成为实现或验收结论。
- 产品整体能力没有混入项目范围，原型不成为业务实现证明。
- 正式文风清理不删除真实边界；待确认保留策略没有被擅自改变。

按用户反馈局部编辑文件，避免反复重印或重做已认可内容。格式转换不扩展功能、变更硬性指标或忽略失败边界。

完成条件：覆盖表全部有归属，读过所有用例，无跨章节冲突。

## 独立读者检查

生成 5～10 个符合受众角色的问题，例如：
- 从哪里进入，需要哪些权限和配置？
- 操作后什么数据改变，哪些条件不能执行？
- 重投、断线或数据库失败时怎么办？
- 统计单位和计算公式是什么？
- 哪些能力被裁剪，哪些仅保存参数？
- 硬性上限是什么？
- 接口成功是否等于最终业务或物理执行完成？

环境支持且当前授权允许独立子代理时，仅提供文档与问题进行读者测试，不传作者希望的答案。否则按读者视角自行检查，不能冒称独立代理测试；也不必强制用户另开会话。

修复有依据的问题，复核受影响用例。保留模式允许读者明确识别尚未确定的内容；最可能方案模式要求业务规则可独立理解。

完成条件：读者可仅凭正文回答关键问题，或从范围与待确认说明得知边界。自动校审不表示客户确认、代码测试通过或现场验收。
